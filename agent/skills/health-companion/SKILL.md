# Health Companion

仅在用户明确询问自己的健康记录、变化趋势或要求整理一条待审核记录时使用本 Skill。必须以当前
Profile 实际提供的工具为能力真相，Skill 文字本身不授予写权限。

## 操作顺序

1. 默认先调用 `health.summary.read` 获取指定日期的最小摘要；日期不明确时先询问用户。
2. 只有用户询问变化时才调用 `health.trends.read`。只使用工具返回的聚合统计，不反推逐日值；
   `heart_rate` 表示手表全天记录的日最低心率代理，不等同于临床静息心率。
3. 只有独立 Health Profile 的当前工具目录明确包含 `health.records.draft` 时，用户要求记录后才可
   复述日期、类型与字段并创建草稿。
4. 在统一 Shadow Nexus Profile 中，明确记录意图应生成结构化 Proposal，由隐藏 Host 按
   current_intent 调用 `health.records.write`；不要求用户切换页面或重复确认普通 L0–L2 记录。
   只有领域回执为 `committed` 才能声称已保存。
5. 常见食物且用户允许估算时，优先复用同一用户已授权的历史规格，再结合包装、订单、照片和
   食物库估算；名称保持干净，数量、做法、估算依据与误差写入备注。缺少会改变业务含义的必填
   事实才追问，不为可合理估算的克重和热量反复打断。
6. 独立旧 Profile 实际创建草稿后返回引用与 `pending` 状态，明确说明它尚未成为正式健康记录。
7. 403/404 后停止，不猜测 Profile ID、其他资源或机器凭据。
8. 当前目录提供 health.weekly.evidence 时优先复用其确定性比较；覆盖不足、来源变化或权限撤销时不补算。
9. health.data.status 只描述服务端已知状态，不能推断蓝牙故障。修改已有事实必须使用新命令与最新版本，不能延用旧批准。

## 健康安全边界

- 不把模型输出描述为诊断、治疗方案、处方、医疗器械结论或紧急医疗判断。
- 不根据单个数值自行判定疾病；缺失、设备误差和测量条件必须作为不确定性保留。
- 当用户描述明显异常、持续恶化或紧急症状时，建议及时联系合格医疗专业人员；疑似紧急情况
  应建议使用当地急救或紧急医疗渠道，不能只依赖 Agent。
- 不索取或展示合同之外的血压、血氧、化验原始值、完整记录导出或其他高敏数据。
- 没有正式写入工具或未收到 committed 回执时，不声称已经正式写入、批量修正、删除或导出。

字段与披露边界见 [references/data-boundaries.md](references/data-boundaries.md)。
