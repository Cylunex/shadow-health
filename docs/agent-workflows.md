# Health Agent 工作流：实施与上线说明

日期：2026-09-04。对应 [改造方案](agent-evolution-plan-2026-09-04.md) 的 P0–P4 可开发范围。
已实现服务端与 Shadow App 客户端代码；本文件不代表生产已部署或真实设备验收已通过。
当前产品仍为单人 primary Health 档案，不宣称多租户健康库隔离。

## 1. 用户入口

- 首页：保留开秤，增加原生阶段与本次服务端状态；待审核数量链接到健康助手。
- 报告/我的 → 健康助手：一餐审核、任务回执、证据复盘、小行动、偏好和主动整理。
- 内置 AI：最小日常事实问答；所有模型记录只生成草案。
- 饮食照片识别：一餐一稿，核对或修改后确认；不会自动写饮食或食物库。
- 手工表单：继续直接保存，不增加二次审核。展示指标与手工录入指标仍分别控制。

## 2. 调用方与写路径矩阵

| 调用方 | 新路径与边界 | 发布时要做的事 |

| 内置 AI / 照片识别 | shared draft service；登录身份；没有 commit 工具 | 更新 Health 服务即可；独立识图配置继续生效 |
| MCP / 外部 Agent | machine v1；独立主体；稳定幂等键；只读或 draft | 更新启动环境、工具列表和 mcp_server/skills 提示 |

## 3. 事实与审核不变量

- 草案内容两天内有效，修订生成新 ID，旧稿拒绝；Nexus 同 ID revision 为 1，传入不同版本/hash 拒绝。
- 浏览器确认绑定 payload_hash；机器提交逐请求校验主体、audience、scope、Profile grant。
- 行锁和事务保证并发双击只落账一次；同幂等键不同内容冲突；成功后重放返回相同回执。
- 餐次/份量/营养/备注可在审核卡调整。食物库项按重量服务端计算，可显式切换为手填快照。
- 修正饮食保留 before 版本，不删除重建；原记录变化、照片删除、过期或拒绝后不能继续批准。
- 自动采集来源的指标不允许 Agent 覆盖；手工表单仍是用户自己的编辑入口。
- 确认后读回实际 DietLog/指标/运动；饮食显示当日数据库总量，缺失不是 0。
- 模型/OCR/备注按不可信文本渲染，不能执行 HTML、隐藏工具、任意 SQL、Shell 或导出。
- 审计只记主体、操作、引用、状态，不保存 Prompt、凭据或健康正文。

## 4. 数据管家

每次原生开秤生成 UUID，采集、权限、上传、排队与服务端接收状态绑定该 attempt。
旧扫描回调和旧上传结果不能改写新会话；离线记录保留原 attempt。
服务端分别展示测量时间、接收时间、标准化时间；只有 parsed 才称入库成功。
重复消息保留 first_attempt_id，网关无 attempt 的补发不会擦除手机的关联。
旧 APK 无法精确关联时明确显示“本时间窗收到”，不根据缺数据判断蓝牙失败。

机器的 health.data.status 仅公开已知服务端同步状态；修复游标/删除数据等维护操作不对模型开放。

## 5. 证据与确定性复盘

默认比较上个完整星期与再前一个星期，互不重叠。7/30/90 天手动分析也使用两个等长窗口。
复用 MachineHealthService 的摘要/来源口径；只保留体重、睡眠时长、步数和饮食记录热量。
每个窗口至少 3 个有效日、同一来源才输出差值；缺失不填零，饮食覆盖不等于真实摄入完整。
来源指纹、权限和重新同步状态进入证据版本；窗口内来源变化阻止跨期比较。
源数据修订/补传令指纹失效；来源撤销隐藏旧快照；快照 30 天过期并由 worker 清除内容。
用户主动保存的目标基线/结局属于行动历史，保留直到后续显式数据管理，不从聊天重建记忆。

证据页给出覆盖、时区、算法和逐日日报链接。趋势链接明确为“当前趋势”，不冒充历史证据期。
不生成综合准备度、训练风险处方、医疗预警、能量差反推漏记或因果归因。
原始记录仍由既有来源底座保管；此轮不声称补齐早期未留存的原始历史。

## 6. 后台执行

新增五张领域表：health_tasks、health_evidence、health_preferences、health_goals、health_monitors。
没有额外队列/向量数据库/通用 Agent 控制面。任务状态：pending → running → done / failed / cancelled。
PostgreSQL SKIP LOCKED 领取；5 分钟租约、每 5 个分析日续约、运行预算 120 秒检查、最多 3 次领取。
完成时校验租约令牌；取消或其他 worker 重领后，旧计算事务不能发布结果。
失败可在 UI 有界重试，关闭页面和重启 Web 不丢任务；等待审核不占线程。
周复盘由本地确定性计算完成，模型调用次数为 0，结果记录 duration_ms。
交互问答最多 8 次工具调用、8 轮上限；每请求最多预留 12,000 输出 token、64,000 字符工具上下文，
120 秒发起调用预算、单次网络超时 30 秒、无自动 SDK 重试。费用不伪造换算，实际账单以模型供应商为准。
不自动切换供应商重发健康数据；识图未单配时仍使用现有主配置回退。

任务耗时/失败/尝试次数可从 health_tasks 的元数据统计；草案审计含 approve/reject/revise。
上线后再建立真实使用基线，不宣称称重重试次数或录入操作已经降低多少百分比。

## 7. 小行动、偏好与主动性

用户明确采纳有效复盘中的一个小行动，保存版本、期限、感受、暂停/继续/取消和到期结果。
修订保留历史；重复创建同一行动幂等；结果只描述同期变化，不证明因果。
偏好仅三组白名单（少打扰/周度回看、日常/力量、周一/周日），显式保存、一年过期、可遗忘。
遗忘清空偏好值，模型不再获得它；不做聊天自动抽取，不删除健康原始记录。

仅两个监测模板：数据晚到、周度回看。默认关闭。
必须经过至少 7 天且实际观察至少 7 个日期，才能显式开启站内提醒；不开外部推送。
22:00–08:00 安静，支持忽略本次、暂缓一天和永久关闭；少打扰偏好立即隐藏提醒。
周报到期可静默创建持久任务；同周稳定键去重，影子模式只计算不创建正式任务。
本次未等待真实 7 天，不会伪造观察日期来提前启用生产提醒。

## 8. 部署与回滚

1. 盘点实际 MCP/Nexus 调用方；提供独立主体，不赋模型 records:write；备份数据库和上传目录。
2. 更新代码并执行 alembic upgrade head（20260904u21）；这是新增表，不修改历史记录。
3. 启动 Web 和独立 worker：python -m scripts.health_worker。Docker Compose 已包含 worker 服务，等 Web healthy 后启动。
4. 非 Compose 部署使用与 Web 相同虚拟环境、工作目录和受限配置，由现有进程管理器自动重启 worker。
5. 刷新 Platform 的 v0.2.0 合同和 MCP 工具清单；重新生成旧 pending 草案，不再开放 legacy REST。
6. 验证 /readyz、审核/拒绝/重复提交、后台任务和来源权限；之后安装新版 Shadow App 验证 BLE 与离线补发。
7. 先开启影子观察，不直接打开提醒；至少运行一个完整复盘周期再评估。

紧急暂停：HEALTH_AGENT_REVIEW_ENABLED=false 并重启 Web，阻止新的草案落账；已成功的回执仍可读回。
可停 worker/关闭监测；不通过恢复旧 Agent 直写来回滚。已有健康表不删。
迁移 downgrade 会删除五张新工作流表，因此只用于空测试库；生产优先停用功能或从经过验证的备份恢复。
本次没有 NAS 部署、Git 推送或 APK 发布，也没有创建密码脚本。
