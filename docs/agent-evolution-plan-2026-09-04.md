# Shadow Health：证据驱动的日常健康助手改造方案

日期：2026-09-04。状态：P0–P4 可开发范围已实施，详见 [实施与验收说明](agent-workflows.md)；生产发布和现场观察尚未执行。下文保留研究时的判断与范围。

## 1. 结论与范围

建议把 Shadow Health 从“健康记录 + 能调用工具的聊天”升级为“能解释数据、协助记录、持续复盘，但不会擅自改变事实的日常助手”。

这不是重建健康 App，也不是在 Health 内再造 Agent 操作系统。核心闭环是：取得有权限的证据、完成确定性分析、提出有限行动、必要时确认、执行后读回、到期复盘。

优先服务实际使用习惯：频繁称重、三星健康自动同步、Agent 记饮食；减少录入和查看日志的负担。器械训练、复杂训练周期、医疗预警暂不作为主线。

本次依据三份用户材料、当前本地代码和新增公开资料。代码基线为 `eb22f55`（完善活动消耗与餐图资产接入）；没有拉取远程、访问生产 NAS、采集真实健康记录或验证线上部署状态。因此，本文不把代码存在等同于生产启用，也不声称已确认近期故障原因。

## 2. 对三份材料的取舍

| 材料主线 | 保留 | 调整或不采用 |
| --- | --- | --- |
| 纵向健康账本 | 原始记录可追溯、来源隔离、修订留档、质量门槛、可重放 | 先补现有模型缺口，不先统一重写全部 Observation、接入 Timescale 或拆微服务 |
| 本地分析与准备度 | 本地确定性计算、趋势解释、低成本分析 | 暂不推出统一准备度分、训练负荷预警或凭热量差判定漏记 |
| Agent 2.0 行动系统 | 草案审核、长期目标、受控记忆、任务恢复、结果评测 | Health 只做领域工作流；不复制 Platform 控制面、不首期引入六个常驻 Agent 和二十多张表 |

最重要的补充判断：架构治理和用户体验应在同一个功能中交付。不能连续几个版本只有权限、表结构和调度改造，却让用户仍然反复开秤、找回执、修正饮食。

## 3. 代码现状：不能按从零建设排期

| 已核实内容 | 代码或文档依据 | 对方案的影响 |
| --- | --- | --- |
| 新机器合同已有读取、草案、隐藏的审核写入能力 | `agent/manifest.yaml`、`docs/agent-plugin.md`、`app/routers/machine_agent.py` | 扩展现有合同，不另造一套 MCP 权限模型 |
| 草案、机器审计和幂等基础已存在 | `AgentRecordDraft`、`AgentMachineAudit` | 补版本、失效和执行回执，不从新 Proposal 系统起步 |
| 原始修订、字段来源、同步游标、质量摘要已存在 | `docs/health-data-foundation.md`、`app/models.py` | 先建立跨功能一致的证据引用和计算口径 |
| 原始记录并非全历史完全不可变 | 当前 `import_raw` 会更新，旧内容进入 `import_raw_revisions`；早期未留档部分不可恢复 | 不能承诺重放出过去所有状态；只对真实留存范围提供保证 |
| 旧 MCP 与旧 Agent API 仍保留共享 ingest 凭据路径 | `mcp_server/server.py`、`app/routers/agent.py`、`app/routers/ingest.py::_bearer_reject` | 新合同已严格，不代表旧调用路径已迁移；先盘点实际调用者 |
| 内置 AI 仍会直接执行写工具 | `app/services/llm.py::ask`、`app/services/ai_tools.py` | 必须一起迁移；执行后展示写操作，不等于执行前审核 |
| 有 `ImportJob`，但部分 AI 分析仍使用 daemon thread / AppSetting 状态 | `app/models.py`、`app/routers/ai.py`、`app/routers/agent.py` | 不说“没有任务系统”；针对需要重启恢复的分析任务补持久执行 |
| 首页已有开秤与本次接收反馈 | `app/routers/scale.py::today_scale_status_fragment` | 优化关联准确性和阶段反馈，而非重新新增入口 |
| 首页秤反馈当前按时间窗查 `miscale` 最新原始记录 | 同上，查询 `last_seen_at >= scan_started` | 时间窗只能作为关联启发式；重复上报或邻近事件需专门测试 |
| 当前已有 OIDC 和统一平台接入 | `docs/sso-migration.md`、`docs/agent-plugin.md` | 不再把“新增登录”列为改造第一步 |
| 独立 Shadow App 已有正式 release 签名配置，targetSdk 为 35 | 相邻 `shadow-app/app/build.gradle.kts` | 不能把旧 `health/android` 壳的结论直接套到现用客户端；手机安装版本本次未核实 |

旧通道保留是策略收敛问题，不是在没有验证入口保护和部署配置的情况下判定“公网无认证漏洞”。设备上传凭据与 Agent 凭据应分别盘点，不能为了关闭旧 Agent 路径而顺手切断秤或三星同步。

## 4. 新资料与值得借鉴的机制

以下区分“原材料提到、本次复核”与“本次补充”。日期是论文提交/文章发布日期；持续维护文档以本次访问日为准。论文、开源仓库和工程文章都不等于生产可靠性或临床有效性证明。

### 4.1 健康 Agent：借机制，不整体搬项目

| 项目 / 文章 | 时间、性质 | 借鉴与取舍 |
| --- | --- | --- |
| [Google：The anatomy of a personal health agent](https://www.research.google/blog/the-anatomy-of-a-personal-health-agent/) | 原材料已提；研究团队介绍 | 数据分析、领域解释、行为支持分工。落地为按需步骤，不让每次查体重都运行多 Agent |
| [WEQA](https://arxiv.org/abs/2606.18147) | 2026-06-16；预印本；复核 | 按问题选分析工具和执行计划、再审查回答依据。用于“先确定要算什么”，而非全文数据塞进上下文 |
| [HealthClaw](https://arxiv.org/abs/2607.13940) | 2026-07-15；预印本；复核 | 分开共享规则与个人长期记忆；一次对话后的内容不应全变成永久事实。其离线评测不能证明临床效果 |
| [HiMe](https://arxiv.org/abs/2607.21019)、[源码](https://github.com/thinkwee/HiMe) | 2026-07-23；研究平台；复核 | 实时事件与长期数据结合、分析结果可追踪。不要照搬任意 SQL / Python 和自动生成页面的权限边界 |
| [HiMe 作者：Lessons from Burning 1.7B tokens](https://thinkwee.top/2026/04/26/AgentHarness/) | 2026-04-26；本次补充的作者工程复盘 | 个体事件流、低成本触发器和可控主动性，比一味提高自主运行频率更值得借鉴；属于个人工程经验 |
| [Open Wearables](https://github.com/the-momentum/open-wearables) | 持续维护项目；复核 | 统一多供应商接入、面向 AI 的数据接口。以后确实新增设备供应商再评估；不替换已工作的本地秤和三星链路 |

HiMe 自己的[安全说明](https://github.com/thinkwee/HiMe/blob/main/SECURITY.md)指出：默认代码工具可在进程内执行；配置外部模型时健康数据会发给该供应商。自托管存储不等于没有外发，不能把研究项目的宽工具权限当作本项目默认配置。

### 4.2 本次新增的工程方案：比增加 Agent 数量更直接

| 新增参考 | 提炼出的设计 | 本项目采用方式 |
| --- | --- | --- |
| [Pydantic AI Deferred Tools](https://pydantic.dev/docs/ai/tools-toolsets/deferred-tools/) | 工具调用暂停、输出待审批请求、取得外部结果后恢复 | 审核卡绑定具体参数；拒绝、修改、超时都是正式状态，不靠聊天里一句“可以”恢复任意旧操作 |
| [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 单次运行检查点与跨会话记忆分离 | 把任务状态、用户偏好、健康记录分开；进程内 MemorySaver 不能满足重启恢复 |
| [DBOS Workflows](https://docs.dbos.dev/python/tutorials/workflow-tutorial)、[架构](https://docs.dbos.dev/architecture) | 数据库持久工作流、步骤记录与稳定工作流标识 | 若现有运行时不能提供所需恢复能力，可做小型技术验证；不预先引入另一套控制面 |
| [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 2026-01-09；区分任务、运行轨迹和最终结果，组合确定性与人工评分 | 不只评回答是否好看：检查实际写了几条、是否越权、重启后是否重复、是否真的减少操作 |
| [τ²-bench](https://github.com/sierra-research/tau2-bench) | Agent 与用户共同改变环境的评测方法 | 测试用户在另一个页面改了草案、设备补传、审批发生延迟等并发情况，不移植其业务数据集 |
| [AgentDojo](https://github.com/ethz-spylab/agentdojo) | 较早的安全基准，并非 2026 新项目；测试工具返回中的提示注入 | 把餐饮备注、OCR、导入文本中的恶意指令加入本项目测试集 |
| [MCP：Tool Annotations as Risk Vocabulary](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/) | 2026-03-16；annotations 是提示，不是强制权限 | 所有写入、敏感读取、外发约束必须在服务端和运行环境执行，不能靠工具描述保证 |

选型结论：本轮先采用这些模式，不直接增加 Pydantic AI、LangGraph、DBOS 三套依赖。已有 DSH/Platform 能提供的运行能力优先复用；Health 保留自己的业务执行状态。只有明确的恢复需求无法满足时，才单独验证一种工作流实现。

## 5. 架构边界：统一入口，领域负责事实和行动

依据相邻项目 `shadow-platform/docs/unified-agent.md`，Platform 已承担统一控制面职责。建议职责保持如下：

| 组件 | 应负责 | 不应负责 |
| --- | --- | --- |
| Platform | 身份、能力合同、Profile 策略、构建发布 | 健康原始记录、健康计算口径、集中保存健康 Prompt |
| DSH / 统一 Harness | 通用对话循环、能力选择、运行预算、通用恢复能力 | 绕过 Health 业务校验直接写数据库 |
| Health | 证据查询、确定性分析、健康草案、领域任务、目标与结果 | 再做全局 Agent 注册表、通用模型网关和万能记忆服务 |
| Nexus / Health UI | 确认界面、待办入口、执行回执和证据查看 | 成为第二份草案真相或自行决定授权 |
| Shadow App | 设备采集、原生开秤、权限状态、离线上传、原生阶段事件 | 本地伪造服务端入库成功 |

普通查询只做一次有限工具调用；复盘才进入分析流程；记录才走草案；后台规则先做便宜判断，需要解释时才调用模型。模型不可自行增加工具权限或无限创建后续任务。

### 5.1 能力收敛

1. 保留现有 `health.summary.read`、`health.trends.read`、`health.records.draft` 与受控审核能力。
2. 新增能力必须有实际产品入口。首批候选是数据接收诊断、指定证据读取、一次复盘任务；名称在合同评审时确定，不在不同客户端各造一份。
3. 内置 AI、旧 MCP、Nexus 最终调用相同的领域草案/执行服务；不要求内部调用绕一圈 HTTP，但必须使用同样的身份上下文和权限检查。
4. 迁移顺序：列调用方 → 新路径覆盖同等功能 → 切调用配置 → 观察使用与拒绝日志 → 关闭旧 Agent 写路由。不能通过故意保留可绕过审批的老通道来回滚。
5. 面向模型不提供任意 SQL、Shell、NAS 管理、数据库修复、用户权限变更或无限网络请求。

## 6. 首批三个端到端功能

### A. 数据管家：今天的数据到了没有

用户价值：不用打开状态页猜测，也不用因“没数据”误以为今天状态变差。

- 保留首页开秤；展示本次状态、收到的数据时间、是否新记录/重复、来源以及最终投影是否可见。
- 区分设备采集时间、客户端发送时间、服务端接收时间、标准化完成时间。前端“刚更新”不能替代真实测量时间。
- 在现有时间窗回显上增加可关联的 attempt/session 标识；如果广播不能直接绑定请求，显示“本时间窗收到”，不要声称精确关联。
- 优先复用已有设备状态事件；缺失时再在 Shadow App 加事件和关联 ID。没有客户端遥测时只能说“服务端未收到”，不能断言蓝牙扫描失败。
- 区分未上传、排队重试、已收到待解析、解析失败、重复已处理；旧会话事件不能覆盖新会话卡片。
- Agent 能解释已知状态、跳转到相关证据；重新同步等维护动作必须使用白名单操作并明确确认，不能自行改游标、改源优先级或删数据。

一期可服务端改善状态与证据页；完整客户端采集链路若缺遥测，需要更新实际 Shadow App。是否需要 APK 以实施前核对现有桥接协议为准。

### B. 饮食助手：少输入、一次核对、明确回执

用户价值：照片或一句话生成一餐，只有真正不确定的内容需要处理。

- 输入可以是文字、照片或修正上一餐。食物库命中、用户给定重量、模型估算分别标注，热量和宏量由服务端计算。
- 置信不足先问最影响结果的一项，例如份量；不要为每个食材重复追问。
- 一餐一个审核卡：日期/餐次、食物与份量、备注、估算标志、图片引用、与原记录的差异。
- 批量确认只覆盖卡片中明确展示的条目和版本，不是给 Agent 的长期写权限。
- 无需审批的显式手工保存仍正常保存；“用户亲自提交表单”不应被迫再批准一次。模型推断形成的草案必须遵守审核合同。
- 成功后显示真实回执和当餐/当日读回结果；超时显示“结果待确认”，不盲目重试为新记录。
- 修改已有餐先生成差异草案，不用删除重建掩盖历史；图片和备注沿用既有资产及授权机制。
- 识图沿用已有独立模型配置与回退逻辑；不为了这轮方案改回共用配置。

默认不新增每餐推送。用户主动录入时就地完成；后台草案集中到“待处理”，避免三餐都变成消息轰炸。

### C. 每周复盘：先解释变化，再决定要不要行动

用户价值：清楚知道体重、睡眠、活动的变化和数据是否足够，不看一串没有解释的分数。

- 首期复用现有周报聚合与趋势能力，补统一证据快照；不是再做另一套周报计算。
- 默认关注体重趋势、睡眠时长/规律、活动与饮食记录覆盖，不以训练表现为中心。
- 每条结论能展开时间范围、有效天数、缺失、来源切换、计算方法及关联原始记录。
- 数据稀疏、换设备、跨时区或补传时，先降级或提示口径变化，不把缺失当零或强作趋势。
- 一次只建议一个可选行动，例如调整记录习惯或试行更稳定的作息；不自动设热量目标、不自动开训练计划。
- 用户采纳后才建立带期限的目标；到期比较执行情况和数据变化。只能报告相关变化，不能把同时发生的变化归因于建议。

复盘可先由用户点击；后台自动生成和通知要在影子运行验收后显式开启。

## 7. 证据、分析和记忆的最小设计

### 7.1 证据快照

在现有来源与质量字段上增加统一的证据响应结构：资源标识与版本、Profile、时间范围及时区、有效样本/预期覆盖、缺失原因、来源/设备、算法版本、生成时间、过期条件、权限范围。

快照按已授权资源组织，不复制一份完整健康库。按需保存支撑结论所需的最小聚合事实或受控引用；保留期限与源数据权限一致。读取链接和缓存结果时再次鉴权，不能靠“链接难猜”保护。

迟到数据、数据修订、用户删除、更换授权或计算版本变化，应令关联结论/待执行草案失效或提示重新计算。不是所有旧建议都静默改写；已展示历史应保留其当时的版本和“现已过期”状态。

### 7.2 确定性分析优先

- 数字、单位、时间窗和差值来自服务端事实槽位，模型负责组织解释；第二个 LLM 可以辅助审查措辞，不能成为唯一事实校验器。
- 分清测量值、估算值、推断和建议；不把设备最低心率代理值写成临床静息心率。
- 沿用已有覆盖门槛，再针对每个新分析函数分别定规则；不能用一个通用阈值允许所有健康结论。
- 基线明确排除当前待比较窗口，按来源/设备/时区口径计算；换设备需提示或重建基线。
- 暂不采用统一加权准备度、ACWR 固定阈值、固定能量系数反推“漏记”。这些在本项目数据上的适用性与误差尚未验证。
- 复现承诺针对证据和计算结果，不承诺模型每次产生完全相同的文案。

### 7.3 受控记忆

第一版只保存用户明确的偏好与约束，例如“少打扰”“暂不做器械训练”“周末复盘”，不要把整段对话向量化作为默认记忆。

候选偏好来自模型时要可确认、可编辑；记录来源、确认时间、适用范围、有效期。健康事实仍查询事实库，不把一次测量复制成永久个人标签。用户暂时的行为不自动解释为长期偏好。

“自律/释放”、化验、血压、血氧等敏感内容不默认进入通用复盘、长期记忆或通知正文。以后若开放单次分析，需要短期且资源限定的授权；首期不扩展其读取范围。

遗忘需要移除该记忆及其派生摘要/缓存，并阻止从保留对话再次自动提取；但不把“忘记偏好”误当作删除健康原始记录。界面要清楚区分二者。

## 8. 可靠执行与审批

### 8.1 审核绑定的不是一句“同意”

在现有草案与 Nexus 审核合同上补齐并测试：用户/机器身份、Profile、操作类型、规范化 payload 摘要、目标记录版本、证据版本、过期时间和一次性执行约束。

用户修改份量、目标记录被更新、授权被撤销或草案过期后，旧批准不得继续执行。用版本比较和数据库事务做强制校验，不靠模型判断“意思差不多”。

同一次提交重试使用同一幂等键；同键不同 payload 拒绝。数据库落账与本地待发送事件尽可能在同一事务写入。跨服务按“可能重复投递 + 幂等处理 + 读回核对”设计，不宣称框架能自动保证所有外部副作用恰好一次。

### 8.2 任务恢复

Health 只持久化自己的业务任务，例如周报生成与批准后执行。先核对现有运行时可复用能力；对仍由进程线程承担的任务补明确状态、租约/心跳、超时、重试上限、取消和稳定任务 ID。

待确认任务不能长期占住线程。重启后重新检查授权、草案版本与证据有效性；外部调用结果不明时先读回，不再生成新写请求。

模型调用按任务配置工具调用次数、最长运行时间、token/费用预算和模型回退。普通数据查询不调用大模型；成本失败不应触发无界上下文压缩/重试。

### 8.3 最小持久对象

| 阶段 | 对象 | 原则 |
| --- | --- | --- |
| 首批 | 既有 AgentRecordDraft、AgentMachineAudit | 增量补充，复用审核权威来源 |
| 首批 | 证据快照 / 分析产物 | 按需要持久，不先另建全部原始事实模型 |
| 首批 | 领域 Job 与必要 Outbox | 先评估现有 ImportJob 与运行时职责，不能拿导入表硬塞所有 Agent 状态 |
| 后续 | Goal / PlanVersion / CheckIn / Outcome | 先承载一个采纳的行动及复盘，不做完整项目管理软件 |
| 后续 | Monitor、偏好记忆 | 用户开启后才有，独立停用/删除/过期 |

具体物理表数量由第一批功能的数据生命周期决定，不在研究阶段一次性承诺二十多表。

## 9. 页面与主动性：让 Agent 减少操作

不强制更换现有模板/HTMX 技术栈。先调信息层级、组件状态和跨页深链接，再用移动端真实流程判断是否需要更换前端框架。

| 入口 | 首屏内容与交互 |
| --- | --- |
| 今日 | 固定开秤与本次状态；最新体重、睡眠、活动；最多一张值得关注的解释；待处理数量；手动录入折叠 |
| 饮食 | 当日餐次、真实/估算标记；拍照或文字记一餐；就地批量审核；回执和修正入口 |
| 趋势 | 一次以一个指标为主；时间范围和来源清晰；解释可展开，不堆多图和多评分 |
| 复盘 | 本周变化、证据是否充分、最多一个行动建议、上次行动结果 |
| 待处理 | 草案、确实需要用户处理的数据问题；完成项自动归档；不显示一屏内部工具日志 |
| 设置/数据来源 | 同步细节、权限、Agent 自动化、记忆；展示指标和可录入指标继续分别配置 |

页面不一定新增六个一级导航；先把“待处理”作为数量入口和抽屉，复盘复用原报告页面。所有跳转携带日期、餐次、指标、证据或草案 ID，返回后保留原筛选与滚动状态。

主动性采用逐级启用：仅应答 → 站内静默整理 → 用户开启的周报 → 少量用户开启的规则提醒。默认无新增外部推送；同一问题合并、冷却、去重，支持暂缓和永久关闭。

首批规则候选是“数据晚到/采集异常”“用户开启的周报到期”，而不是异常心率或训练风险。触发条件用白名单结构描述，由服务端校验并执行；不保存 Agent 生成的任意脚本或自由 SQL。

影子运行仅计算会产生什么提示，不写健康记录、不对外通知。提醒以数据和规则版本去重；补传修复后取消过期提醒。没有新信息时不为了体现 Agent 存在感发消息。

## 10. 分阶段交付与验收

估算为单开发者、现有基础可复用时的有效开发时间，不是交付承诺；跨仓库联调和设备现场验证另计。阶段按验收门槛推进，可独立暂停。

| 阶段 | 主要交付 | 验收门槛 | 粗估 / APK |
| --- | --- | --- | --- |
| P0 基线与边界 | 真实调用方清单；路由/能力矩阵；三条用户旅程测试；现有任务恢复能力核对 | 不把 legacy 和新合同混为一谈；每条写路径有责任人/迁移方案；测试有明确最终状态断言 | 2–3 天；不需 APK |
| P1 饮食闭环 | 内置 AI 与实际使用的旧客户端写入收敛；一餐审核卡、差异、幂等、真实回执 | 未批准不能变更正式记录；重复提交只执行一次；超时可查结果；一餐通常一次确认 | 4–7 天；通常服务端，取决于客户端协议 |
| P2 数据管家 | 复用首页开秤反馈；补阶段与关联证据；同步问题解释、深链接 | 新旧会话不串；重复消息不算新记录；无遥测不猜设备故障；收到但解析失败可定位 | 3–5 天服务端；补原生事件时另需 APK |
| P3 有据复盘 | 统一证据、确定性分析、持久周报任务；复盘 UI | 缺失/迟到/换源/跨日样例正确；重启可恢复；数字可复算；来源权限撤销后不可读 | 5–8 天；不需 APK |
| P4 少量长期能力 | 用户偏好；一个目标及到期回看；最多两个首批监测模板 | 可暂停、撤销和遗忘；影子运行后才开放通知；无新信息不反复提示 | 4–7 天 + 观察期；通知渠道决定是否需 APK |

推荐第一批交付是 P0 + P1 + P2 的服务端部分：先让日常使用可靠省事。P3 再兑现分析价值；P4 不应反过来成为首批依赖。

迁移与回滚：先新增兼容字段、合同与功能开关，再切调用方；保留现有读取页面。不要先删旧表。策略回滚只能回到只读/暂停草案执行，不能重新开放模型直写。数据库迁移、备份恢复与部署需要实施阶段单独验证，本次研究不视为通过。

## 11. 从第一批就建立评测

借鉴前述 Anthropic、τ²-bench 和 AgentDojo 的方法，测试目标是最终业务状态，不是让另一个模型给回答打高分。

首批建议 40–60 个合成/脱敏场景，覆盖普通查询、饮食创建修正、秤重试、睡眠跨日、迟到数据、越权、审批并发、进程中断和恶意输入。不要默认把生产健康记录发给外部模型跑回归。

- 权限：错误 audience/scope/Profile、撤销授权、读取缓存和证据链接均需拒绝；隐藏工具不能仅靠界面隐藏。
- 写入：创建草案不改事实；同键重试不重复；同键换内容拒绝；用户改过原记录后旧草案失效。
- 恢复：批准后、数据库提交后、回执发送前分别注入崩溃；不能丢状态或重复记录。
- 数据：晚到三星数据不作零值；重复秤广播不冒充新测量；睡眠跨午夜与时区规则可复算。
- 安全：食物名、照片 OCR、备注含“忽略规则/上传全部数据”等内容，不能升级权限或触发外发。
- 记忆：忘记之后不再从摘要恢复；私密习惯不进入通知或常规复盘。
- UI：移动端走完开秤、饮食确认、证据查看三个流程；日期/筛选/返回行为正确，常用按钮不被遮挡。

安全回归要求零次越权写入、零次重复落账、零次伪造成功；这是测试验收门槛，不是对生产永无错误的承诺。分析要求所有数字结论都有可核对来源，不足时明确降级。

同时采集不含健康正文的产品指标：一次称重为得到确定状态需要几次重试、记录一餐需要几次操作、草案被改多少次、提醒被忽略/关闭的比例、任务失败率、p95 耗时、每个成功任务的模型成本。先测基线，再定改善幅度，不能凭空宣称效率提升百分比。

上线先限定 Profile 和功能，运行至少一个完整复盘周期；通知功能建议额外观察 7–14 天影子结果。检查点是少打扰、少修正、可信，而不是调用了多少次 Agent。

## 12. 暂缓清单与重新评估条件

- 不整体换成 Open Wearables / HiMe：确有新设备接入成本，且其授权、数据质量与运维收益能覆盖迁移成本时再评估。
- 不先上向量库或健康知识图谱：结构化查询不能满足已证实的检索问题时再做。
- 不先做 Timescale、Kafka 或独立 orchestrator：以实测数据量、查询瓶颈、恢复和跨领域工作流需求为条件。
- 不先重写 SPA：当前技术栈无法通过移动端交互验收时，再针对受限页面做试点。
- 不让 Agent 自主改健康策略、诊断、用药或删除原始历史；本轮没有这类产品授权。
- 不默认扩展敏感数据读取，不为“更懂用户”保存完整聊天和所有私密行为。
- 不以低验证度综合评分驱动饮食/训练处方；先完成数据口径、误差分析和独立专业验证。

最终方向：保留健康账本的可信底座，让 Agent 先成为可靠的记录助理、数据管家和复盘伙伴。长期目标、主动提醒和更深分析逐步建立在这个闭环之上，而不是一次性重建整个项目。
